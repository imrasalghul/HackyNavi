# Navi31 firmware-first admission

Audit scope: the first macOS attachment to a firmware-posted, bare-metal Navi31. The native first-attach contract and console reservation are now implemented below, but not connected to Device activation or demonstrated on hardware. No GPU writes were performed during this audit.

The startup cycle can be removed by separating **firmware-first initialization** from **retirement of driver-published DMA**. Linux initializes owned memory and PSP before multimedia hardware. It does not first wake VCN/JPEG to prove their unused queues drained. Therefore the proposed cold path should leave untouched multimedia engines alone until ordinary post-PSP SMU initialization. The experimental `early_media` protocol remains disconnected; it is unnecessary for this sequence.

## XNU memory and console ownership

Pinned XNU is `xnu-11417.140.69`. [`i386_vm_init.c:468–538`](https://github.com/apple-oss-distributions/xnu/blob/xnu-11417.140.69/osfmk/i386/i386_vm_init.c#L468-L538) treats EFI Loader/BootServices memory as usable RAM, while runtime and nonconventional ranges are excluded. A kext cannot retroactively preserve unknown firmware host-DMA buffers after those pages may have been reused. Firmware-first initialization relies on the firmware handoff having no driver queues; prior-owner activity requires reset/retirement. BME-off contains new PCI traffic during setup but cannot certify internal VRAM activity or retire already issued transactions.

[`pe_init.c:192–229,262–266`](https://github.com/apple-oss-distributions/xnu/blob/xnu-11417.140.69/pexpert/i386/pe_init.c#L192-L266) retains the initial physical EFI console base and copies console metadata. Rotation90/270 swaps dimensions, so this helper explicitly rejects nonzero rotation. [`video_console.c:2652–2721`](https://github.com/apple-oss-distributions/xnu/blob/xnu-11417.140.69/osfmk/console/video_console.c#L2652-L2721) uses explicit `v_length` or pitch×height for its mapping, then adds `v_offset` for pixel access. At2682–2688, a later VM-era input can be virtual; bit0 marks physical and physical decoding strips both low bits. Thus the wrapper must establish address provenance/decode tags, not pass every raw PE base as physical or translate an arbitrary virtual pointer.

XNU first rounds the declared mapping length, then [`io_map.c:92–96`](https://github.com/apple-oss-distributions/xnu/blob/xnu-11417.140.69/osfmk/i386/io_map.c#L92-L96) rounds again after adding the physical page offset. A four-byte image at physical BAR+`0x2004` maps two pages. The helper's `pages` output preserves both; its `bytes` output describes the declared interval. Preserve all mapped pages until CPU console ownership and GPU fetches have both ended.

The real SDK at commit `3f750085caa17ec3a7880f11c11bf4f48cd6a164` exposes `IOPlatformExpert::getConsoleInfo(PE_Video*) -> IOReturn` in `.research/MacKernelSDK/Headers/IOKit/IOPlatformExpert.h:241`. Native code can call `getPlatform()->getConsoleInfo(&video)` virtually; a direct `PE_current_console` import is unnecessary. It still requires normal IOKit superclass/platform symbol linkage. An object compilation alone is not proof of target kext linking/loading.

For display takeover, the SDK's `IOFramebuffer.h:581–587` requires hardware initialization in `enableController`. The public [IOGraphics `IOFramebuffer.cpp:8440–8460`](https://github.com/apple-oss-distributions/IOGraphics/blob/main/IOGraphicsFamily/IOFramebuffer.cpp#L8440-L8460) disables the platform console before this callback. That IOGraphics link is a public family reference, **not a pin of the installed macOS15 binary**. First-fence compute work can preserve the existing console and its reserved pages without changing the display. A modeset requires the proper framebuffer handoff.

## Minimum proposed native sequence

1. The real Device owner serializes PM/reset/removal/mailbox/register actors, verifies identity, assigned BARs and D0, and creates a one-use first-attach state. Record actual epochs; do not assume `PowerGeneration==1` because initial PM registration already changes it. Consume the state before the first control write. Do not recreate it after a failed activation or suspend/reset.
2. Read fresh posted state and sOS through bounded valid MMIO. sOS nonzero, unavailable identity/registers, unposted hardware, previous publication, or a recovery path cannot use firmware-first admission. Reset/repost through the existing native reset protocol or reject. sOS zero plus posted BIOS is the cold classifier; do not label it global quiescence.
3. At the activated owner's entry, clear PCI BME with readback. Preserve current console/DCN and firmware reservations. Stop inherited DMCUB before inspecting a stable surface inventory, quiesce CP/SDMA through their existing actual protocol, and keep separate checks/protocols for other possible boot producers such as LSDMA/IH/display writeback. Deferring VCN/JPEG must not silently remove those checks.
4. Build the union of decoded ROM/runtime firmware tail, discovery, training, actual display surfaces/cursors and the platform console mapping. First-attach absence of previous driver queues supplies a **cold contract**, not a fabricated complete-drain result. Existing explicit reservations remain protected. Fail incomplete or unsupported display inventory; do not infer it from this single console range.
5. Allocate and retain owned GART/PSP/queue storage. Upload GART, install MMHUB and flush while BME is off; then enable BME with fresh readback before firmware DMA. This is a conservative port containment policy based on Linux's memory-before-IH ordering. It does not release or overwrite prior-driver storage based only on BME.
6. Load PSP/SOS/ring/TMR and graphics firmware, initialize normal SMU and graphics queues, then require real GPU-written fence and shader results. The current graphics firmware plan includes SMU/SDMA/CP/IMU/RLC, not VCN/JPEG. Untouched media can remain uninitialized for initial graphics/compute. If media is needed later, use post-PSP SMU power plus the corresponding real media reset/ring initialization before publishing new media storage.
7. From any address publication/control-write attempt onward, keep existing retained-owner, timeout, stop and verified-reset retirement semantics. A later sOS zero or BME-off observation cannot reissue first-attach admission or free hardware-visible buffers. Device PM/stop must wait for retirement; the current diagnostic-only immediate power-off acknowledgement cannot be reused.

## Native call sites and bounded next changes

- `HackyNaviEngineController::start(Operation&)` now requires the actual graphics provider/open-owner binding. After real posted-state/training observations, it consumes the group's one-use `FirstAttach` token (registration of a real retirement handler is mandatory). The token expires with its exact Operation and is never reissued by recovery. Its two pre-PSP media gates now use the distinct `LsdmaResult`/`checkLsdmaStopped` API; the full diagnostic checker remains unchanged. It stops the actual sibling HDA controller before further control writes. The portable early-media wake path remains disconnected.
- `HackyNaviEngineController::makeReservations` now requires that live consumed token plus independent successful LSDMA, CP/SDMA, DMCUB, IH/writeback/MALL and display inventory results. It no longer asserts multimedia drain. Only firmware-first initialization uses the upstream cold convention of no previous driver allocations; the same evidence cannot retire driver-published DMA. Scope checks bracket native startup steps; downstream per-I/O scope propagation and Device binding remain integration requirements.
- `HackyNaviEngineController::start`, `HackyNaviGARTController::enable`: BME-off before NBIO/GART allocation and MMHUB-before-BME-on are now implemented. MMHUB explicitly requires BME off; GFX/runtime checks still require it on. Existing cold checks/stops remain before this containment step; the broader firmware-first admission change is still pending.
- `HackyNaviDevice::setPowerState/stop/systemWillShutdown`: activation needs a retained engine owner and a retirement protocol before acknowledgment/unmap/PCI close. Existing diagnostic capture epochs are useful revocation guards, not proof that DMA stopped.
- `HackyNaviBootConsole` now queries two matching snapshots and records raw address fields. Firmware-first untagged bases must lie inside the assigned target BAR; tagged physical bases are decoded; virtual/unknown addresses fail. Engine unions the validated console pages with DCN reservations and retains the independent DCN completeness requirement. Matching snapshots remain an observation; native console/activation exclusion, persistent reservation and proper framebuffer handoff remain required. No Device activation was added.

## Portable helper delivered

`include/hackynavi/efi_console.hpp`, `src/efi_console.cpp`, and `tests/efi_console_tests.cpp` implement a pure checked conversion from real physical console metadata to one VRAM-relative reservation. The API accepts full-width `physicalBase,rowBytes,width,height,depth,offset,length` and `rotation`. It supports unrotated XNU depths8/16/30/32, requires an already decoded physical base with zero low-two bits, preserves explicit mapping length, validates active-pixel extent and XNU's32-bit geometry/mapping-size bounds, rejects overflow/partial BAR overlap/out-of-VRAM intervals, and includes XNU's double page rounding. Non-Ok output is zero. `NotOnBar` only means the validated mapped-page interval is disjoint from this assigned BAR.

No result asserts complete framebuffer inventory or stops the console. The helper has no IOKit, MMIO, allocation or hardware-test substitute. Validation evidence is written separately to `build/efi-console-report.json` after actual compilation and boundary tests.
